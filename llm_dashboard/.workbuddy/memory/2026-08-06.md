## 远程核查 GitHub Pages 部署（用户推完后帮看，2026-08-06 修正）
- 用 WebFetch 调 GitHub API 核查（无需 gh/登录，公开仓库可匿名读）：
  - 工作流运行：`/actions/runs?per_page=5` → 最新 run 的 status/conclusion
  - 部署状态：`/deployments?per_page=3` 取最新 deployment id → `/deployments/<id>/statuses` → 看最新 state（success/failure/in_progress）
  - job 明细：`/actions/runs/<run_id>/jobs` → 看哪一步失败（log 文本需 admin 权限，匿名 403）
- ⚠️ WebFetch 对同一 URL 有 ~15 分钟缓存！重复查同一 URL 会返回旧结果，误判"一直 in_progress"。务必加 `?fresh=2` 之类查询参数绕过（GitHub API 忽略未知参数正常返回）。
- **本次实测教训（重要）**：8/6 部署（deployment 5777553514, SHA=c45289a）最终 state = **failure**，失败在 `deploy-pages@v4` 步（checkout 与 upload-pages-artifact 均 success → 代码与配置没问题，是部署服务侧瞬时故障）。我上一轮误把中间态 in_progress 当"即将成功/已成功"，被用户纠正。
- 对照：8/3 部署（deployment 5720134043, SHA=82622b0）state = **success** → 证明 Pages 站点正常开启，线上当前运行的就是 8/3 版本（数据到 08-01）。故 8/6 代码虽已上 main，但看板未更新到 08-05。
- **修复**：去 GitHub → Actions → "Deploy dashboard to GitHub Pages" → 找到失败的 run（31092506098）→ **Re-run all jobs** 即可，无需改代码、无需再 push。
- 区分"推送成功"与"部署成功"：远端 origin/main SHA == 本地最新 commit（0/0）= 推送成功；deployment state==success 且线上板块一日期已更新 = 部署成功。两者独立，勿混淆。
